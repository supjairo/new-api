# 错误记录与规则整理

按用户指定的时间范围收集新错误记录，并将可重复识别的错误整理为渠道级错误响应覆盖或流错误覆盖规则。只处理用户明确授权的环境和范围。

## 流程

1. **确认范围**：确定服务器/环境、开始与结束时间、日志类别（通用错误、流错误或两者）、涉及渠道范围。若上下文没有提供某项且不能从已确认的项目配置安全确定，先询问；不得猜测服务器、凭据或时间范围。凭据只使用用户提供的会话信息，不回显、不写入文件。
2. **收集记录**：从日志数据库读取时间范围内的错误记录，保留请求 ID、时间、渠道 ID/名称、模型、HTTP 状态、错误 code/type/message、流事件/结束原因及已有覆盖审计信息。收集只读，不先删除记录。避免输出令牌、用户凭据、上游密钥等敏感值。
3. **归类分析**：按渠道与上游错误语义分组，区分稳定错误模式、偶发网络错误、用户输入问题和无法判断项。对比已存在的 `error_override` / `stream_error_override` 规则及顺序，确认待整理错误是否已经覆盖。不要把“原消息应返回”的错误改写。
4. **拟定规则**：只为证据充分、可稳定匹配的错误拟定规则。优先使用足够具体的状态码和字段路径匹配；覆盖文案必须中性，不暴露上游商家、路由池或内部实现信息。规则按 first-match-wins 排序，精确规则在通用兜底之前。不要合并或删除其他规则来简化配置；保留用户已有规则结构，除非用户明确要求调整。
5. **检查兜底风险**：错误响应覆盖的空 match 兜底只可在用户确认其语义后使用。流错误覆盖的空 match 兜底必须限定在错误事件处理路径中，确认不会匹配正常内容事件。不要将流错误规则混入普通错误响应规则，也不要改变计费、结算、退款或用量统计行为。
6. **先报告并确认**：在任何写库、重启、部署或日志删除前，向用户展示汇总表：记录数量和时间范围、按渠道的错误类别与样例、建议动作（新增/保留原文/不处理）、规则匹配条件与覆盖结果、规则顺序，以及不确定项。明确指出规则表是建议还是已生效。等待用户明确授权后再执行会修改线上配置或删除数据的操作。
7. **应用变更**：严格按确认内容修改指定渠道对应的规则，只增删或调整被确认的规则。写入后回读数据库核对实际 JSON、渠道范围和顺序；配置变更需要按项目现有机制刷新缓存，确有必要时再重启。不得因规则整理顺便修改代码、部署镜像或清理数据。
8. **历史记录清理**：仅当用户明确授权删除时执行。先报告将删除的表、筛选条件、预计数量和时间范围；使用精确时间/类别条件，不得无条件清空整个错误日志表。删除后核对删除数与剩余数。若查询到的时间范围内有记录晚于整理截止时间，不能误删。
9. **验证与交付**：回读渠道规则并检查 first-match-wins 顺序；线上变更后检查服务健康状态和配置生效情况。报告实际执行的查询/修改/删除范围、规则表、日志数量变化、验证结果及未覆盖/未确认项。不要声称完成了未实际验证的步骤。

## 输出约定

- 最终回复必须以 Markdown 表格列出整理结果和当前整体规则；不得只用段落或项目符号汇报。即使没有新增/修改规则，也必须用表格说明现有规则或“无变更”。
- 规则表至少包含：渠道、规则类别、匹配条件、动作（改写/原文返回/不处理）、原始错误消息、覆盖后消息、覆盖字段、优先级/顺序、依据记录数、状态（建议/已生效/待确认）。
- 用中文汇报，错误消息原文与建议文案分栏展示。事实与推测分开；样本不足时标为待观察，不以单条日志推导宽泛兜底。
- 表格外仅可附简短范围、验证结果或风险说明，不可用文字替代表格。
- 不显示密码、API key、访问令牌或其他可用凭据。
